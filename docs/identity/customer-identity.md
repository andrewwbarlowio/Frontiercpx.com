# Frontier customer and enquiry identity

## Contract

The authoritative customer ID is a full, native UUIDv4, generated by Postgres `gen_random_uuid()` when the first accepted enquiry creates a customer. The enquiry ID remains the existing server-generated UUIDv4. Existing enquiry references are not renamed. The database exposes `enquiry_id` as an immutable generated alias of the existing `id`, preserving old integrations while giving new integrations an explicit field name.

Customer is the parent: `customers.customer_id` → `enquiries.customer_id` → notification deliveries through `enquiry_id`. Both parent and child keep their own primary keys. Every enquiry has a non-null customer foreign key; the environment is also checked by the foreign key. A customer with linked enquiries cannot be deleted accidentally. Customer IDs, enquiry IDs and assigned links cannot be routinely rewritten. These references are not access tokens.

Future CRMs must retain Frontier customer IDs as the authoritative external reference and use this same database identity creation contract for new contacts. A CRM's unavoidable internal key must remain separate; it must never replace the Frontier ID. Documents and deals must reference the customer UUID. Export/import must preserve canonical full UUIDs, not truncated display strings.

## Matching is unverified grouping, not authentication

A public enquiry cannot verify who owns an email address. For initial anonymous capture, an exact normalized combination of email, name and phone reuses an **unverified** contact group. This does not establish verified identity or confer access. The public response continues to expose only that enquiry's receipt reference, never the customer ID, contact record or earlier enquiries.

Normalisation is deliberately conservative and implemented in the database: trim/lowercase email without rewriting dots or plus tags; trim/lowercase name and collapse whitespace; remove phone punctuation without guessing country codes. A shared email with conflicting name/phone creates a separate customer and marks the related groups for review. Changed email is not automatically linked to an old person. All contact snapshots remain on the enquiries.

This guarantees stable IDs for the same exact normalized details. It cannot guarantee one record per real-world person without verified identity or operator review. Genuine duplicates must later be reconciled by a restricted, reviewed canonical-alias mechanism preserving original IDs; this change does not add a public merge endpoint or silently rewrite history. No login, OTP workflow, CRM or company identity model is introduced.

## Transaction and compatibility

The existing submission key remains separate from both IDs. The database trigger creates/resolves the customer in the same transaction as the enquiry and outbox. A uniqueness constraint handles concurrent matching details. An identical accepted retry returns the same enquiry/customer pair; deliberately new enquiries retain separate enquiry IDs.

The additive migration backfills customer links while preserving every existing enquiry ID and submitted field. It also supports the old backend during rollout: an insert without `customer_id` still receives one from the trigger. New customer-table permissions are limited to the existing runtime role. Apply the tracked migration before deploying the updated notification reader.

## Notifications

HTML and plain-text internal notification bodies include the exact persisted Customer ID and Enquiry ID in full. The subject now uses the full enquiry reference too. The existing notification recipient remains the explicitly agreed shared mailbox `enquiries@frontiercpx.com`. No personal Andy/Roger addresses have been inferred or added; both receive via whatever access/routing that mailbox has in Microsoft 365.

The existing durable outbox, recipient tracking, retry leases, provider idempotency keys and signed callbacks remain. A failure cannot create replacement IDs. Historic synthetic test notifications remain excluded from sending. Sending must remain disabled until the sending domain and actual inbox delivery are verified; a pending DKIM record does not block database capture.

## Verification

19 automated scenarios pass, including all 26 generated forms, distinct UUIDv4 IDs, repeat-contact grouping, conflicting/shared and changed email, retry identity preservation, immutable IDs, foreign-key restrictions, legacy backfill/rerun, complete notification identity fields, JSON export/import preservation, and no customer identity disclosure in the public API. Embedded Postgres tests do not simulate independent server sessions for advisory locks; deployed Neon checks supplement them.

Before migration, an isolated Neon backup branch preserves the production state. Verify original enquiry count and a hash of the original reference/contact/source fields before and after backfill. Rollback is to compatible old application code; retain the new customer table, IDs and trigger. Do not drop identity data to roll back the application.
